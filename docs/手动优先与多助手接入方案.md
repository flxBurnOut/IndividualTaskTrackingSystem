# 手动优先与多助手接入方案

交接更新：2026-10-03，本方案已纳入 Beta 版本管理。A 与 B1 已在功能提交 `58d7c3e` 实现并推送；当前边界和验证证据以 [开发交接与当前状态](开发交接与当前状态.md) 为准。下文保留 2026-09-29 原设计思路，“建议”“后续”等表述不代表尚未开始或已获新的实施授权。新助手的外部资料仍是原核查记录，本轮没有重新验证，实施前须再读官方文档。

B1 验证（2026-10-02）：标准 focused 首轮 359 项中 358 项通过，发现已删除任务详情不应读取子任务的回归；修复后相关 100 项界面与工作区检查全部通过。最后的大字号表头和滚动布局调整，32 项批量界面检查再次全部通过，并核对真实中文深浅主题截图。当时后台及接口相关 259 项未在仅界面修复后重复运行；2026-10-03 已在 Beta 目录重新实测 259 项通过。未再跑全量或打包验收，临时测试进程与数据均由统一入口回收。

目标是让用户不安装任何外部 Agent、不填 API Key，也能完成记录、整理、安排、执行、反馈和回顾。助手作为可选能力，使用同一份记录。手动体验改造可独立交付，不等待三个新渠道全部接通。

**一、制定方案时的现状判断**

已有的本地业务服务、任务、单日计划、复盘、资料、课表和部分规则可以继续复用。问题分为三层：

| 层次 | 当前问题 | 改造方向 |
| --- | --- | --- |
| 入口与表达 | 空计划、无计划复盘、准备规则等处优先引向 Codex，手动能力在次级按钮或折叠区 | 主要按钮按业务动作命名；未配置助手是正常状态 |
| 手动流程缺口 | 集中任务池、多项快速录入、依赖编辑、课程评分新增、结构化规则新建、无计划反馈缺少顺畅入口 | 接通已有业务能力，减少往返窗口与重复填写 |
| 系统能力缺口 | 批量原子修改、任务拆分、跨日计划依赖、日期范围原子保存、通用重复任务还不完整 | 先定义业务语义和事务边界，再做界面；不能只改名称或增加周视图 |

建议保留现有总览、今天、项目与课程、复盘，并增加集中“任务”入口。任务页中的“未安排／未归属”就是待整理区，沿用原任务身份，不另建一套需要二次转换的任务记录。首次使用默认展示手动流程；设置中提供“显示助手功能”，关闭后隐藏助手入口和连接提示。已经在执行的助手任务仍需有状态入口，关闭展示不能悄悄取消任务。

**二、把日常操作接成完整流程**

| 场景 | 建议的实际操作 | 首批范围与后续边界 |
| --- | --- | --- |
| 记下一件事 | “快速记录”只填标题即可保存；支持保存并继续，日期、归属、估时以后补 | 首批单项录入复用 create；多行粘贴要有逐行预览，批量事务另做 |
| 找出要做的事 | 集中任务页可看全部待办、未定日期、今天到期、未来截止、项目归属；搜索覆盖全部分页 | 首批接统一分页查询，不只筛界面当前已加载的一页 |
| 安排今天 | 主按钮“安排今天／编辑安排”；左侧任务池、右侧当前安排；多选加入、直接新建、拖动排序并保留键盘上下移 | 复用单日 create_plan / revise_plan；未知时间留空，按先后安排；AI 建议放次入口 |
| 调整任务关系 | 详情明确显示“前置任务”“后续任务”；可选择、解除、跳转查看；倒置时指明具体冲突 | 首批接 link / unlink 与查询，复用防循环校验；不凭任务说明猜依赖 |
| 拆开大任务 | 显式“拆分任务”，逐行填动作和完成条件，可勾选依次执行 | 后续系统命令一次创建独立任务及依赖；清单勾完不能自动判定原任务整体完成 |
| 记录执行 | 计划内事项按现有真实反馈保存；没排计划时可选择已有任务或日程“记录实际情况”，也可保存文字小结 | 首批接现有反馈入口；保留“无原计划”，不倒造计划或虚构完成率 |
| 管理课程 | 直接新增笔记、评分项、日程、交付节点；所有记录支持翻页和编辑 | 首批尽量接已有类型与命令；评分权重、成绩、完成状态分别记录 |
| 整理资料 | 拖入、粘贴、预览、命名、归属、查找；资料旁提供“从这里建立任务／记录日期” | 导入只保存资料；本地提取文本不等于内容已被理解。来源定位要保留，AI 摘要另选 |
| 设置习惯 | 手动新建“每日容量／保护休息／提前提醒／文字偏好”；准备规则显示触发节点、提前天数、任务及发生预览 | 首批把已支持的结构化类型开放；无节点的每周例行任务需要后续新增规则模型 |
| 安排一段时间 | 日期范围草稿中按天放置任务，显示固定安排、容量、依赖和改动预览，集中保存 | 后续跨日业务能力；首批不把逐日保存包装为一次原子成功 |

编辑反馈要一致：界面明确区分“草稿未保存”“已保存”“需要处理冲突”。切换日期、关闭窗口时保存或恢复草稿；不能悄悄丢掉当前编辑。小范围即时操作可提供撤销入口，但撤销通过有版本检查的更正命令，不删除反馈历史；全局撤销不列入首批承诺。

制定方案时，单日编辑器允许修改已有任务的完成标准，但服务会拒绝与原标准不一致的计划块。首批应直接显示只读原标准，并提供“编辑任务标准／拆分任务”入口。若以后支持“本次只推进一部分”，应另建本次推进范围与反馈语义，不能降低原任务完成标准来绕过保护。

**三、哪些必须调整到系统层**

1. **批量录入与修改**：预览和提交共用同一批标识及请求号；提交核验每个对象版本；失败不得出现未说明的半批成功。超过上限明确拆批，不伪称无限原子操作。
2. **任务拆分**：在一次事务中创建独立任务、归属及依赖；保留原任务历史和拆分关系。拆分不是向说明字段追加编号。
3. **跨日依赖**：目前只认可前置已经实际完成，或处于同日更早计划块。要支持周一做前置、周二做后续，必须新增“计划上的先后可行”判断；它与“实际已经完成”是两个状态。前置未实际完成时，后续执行仍需提示受阻。
4. **日期范围计划**：统一读取受影响日期的固定安排、容量、任务及原计划版本；有界范围内校验后原子提交。改动受保护历史时拒绝或明确排除；不能覆盖已反馈条目。
5. **通用周期任务**：与围绕课程/截止节点的准备规则分开表达，复用发生次账本和去重；明确停用、节假日、遗漏期间及修改未来实例的行为。

上述能力同时服务手动界面和所有助手。任务顺序、冲突、保存与回执应由本地业务服务保证，不依靠某个模型“记住规则”。

**四、新渠道怎样接，先分清能力**

以下保留 2026-09-29 方案中的官方资料核查记录，本次交接没有重新验证，不代表当前厂商接口仍完全相同，也不代表已在本软件联调通过。软件界面应区分“官方支持”“本机已验证”“未验证／不支持”。

| 渠道 | 建议接法 | 用户获得的能力 | 需要先验证的边界 |
| --- | --- | --- | --- |
| 腾讯云 TokenHub | 本软件直接调用模型 API，管理上下文与工具执行 | 不打开外部 Agent，也能在软件内请求可选建议 | 所选模型的工具调用、结构化结果、超时、限流与使用额度；无外部桌面会话 |
| CodeBuddy Code | 先验证通用 MCP；主动执行优先比较官方 CLI／SDK／ACP，选一条主路线 | 在 CodeBuddy 操作本软件；后续可由软件派发并继续任务 | SDK Preview；Windows 进程、取消、恢复和权限回调需实测；不预先承诺复用任意 IDE 桌面会话 |
| WorkBuddy | 先做 WorkBuddy → 本软件的 MCP 连接；主动派发另做 Open API 验证 | 在 WorkBuddy 读写本地事项；通过验证后再扩展软件主动请求 | 账户授权、消息与业务事项可靠对应、桌面与云端会话的区别 |
| 现有 Codex | 先包装为同一适配接口，保留现有模式 | 老用户继续原会话和事项 | 迁移不得重建旧会话、改变执行中任务或丢失候选 |

TokenHub 官方提供 OpenAI Chat Completions、Responses 与 Anthropic Messages 协议入口，具体支持依模型而异。建议首期用 Chat Completions 的较小能力集；本地保存对话与事项身份，自己执行有白名单和预算的工具循环。部分 Responses 兼容模式限制云端上下文续接，不能把它当作本地任务记忆的替代。[调用概览](https://cloud.tencent.com/document/product/1823/130079)、[工具调用字段](https://cloud.tencent.com/document/product/1823/135872)、[Responses 兼容限制](https://cloud.tencent.com/document/product/1823/133813)。

CodeBuddy 官方 CLI 提供非交互执行、流式输出和会话恢复；官方 Agent SDK 提供会话、权限回调和 MCP 注入，当前标为 Preview；ACP 面向 Agent 与界面解耦。第一步用同一组小型验收比较适配成本，选定主路径后再产品化。[CLI](https://www.codebuddy.cn/docs/cli/cli-reference)、[SDK](https://www.codebuddy.cn/docs/cli/sdk)、[ACP](https://www.codebuddy.cn/docs/cli/acp)。

WorkBuddy 连接器支持本地 stdio 和远端 MCP。Open API 已有 PC 本地助理在线状态、消息及历史，以及云端任务和 ACP 信息；但公开的 PC 消息参数未展示按独立项目／会话选择目标的能力，云端任务也不能等同本机普通会话，因此“一事务一桌面会话”必须另验。[连接器](https://open.workbuddy.cn/docs/connector)、[Open API](https://open.workbuddy.cn/docs/openapi)。

WorkBuddy 第三方应用还涉及登记、权限、回调与审核，公开 OAuth 换票流程使用 client_secret。发布的 EXE 不能内置公共应用密钥；需要确认官方适用的原生客户端授权方式，或增加服务端授权代理。对于坚持纯本地部署的版本，先交付外部 WorkBuddy 通过 MCP 调用本软件的路线。[第三方应用接入](https://open.workbuddy.cn/docs/third-party-app)。

TokenHub 的模型服务、CodeBuddy 的 Agent 订阅／登录、WorkBuddy 的账户与开放应用授权分别管理，不假定同属腾讯就共享密钥、额度或会话。

**五、通用接口只做必要的一层**

保留现有 Core、SQLite、版本检查、候选验证、事务和回执。增加薄适配层，不先建设复杂插件市场。

- 提供方配置：稳定 provider/profile ID、接入类型、模型、超时、费用或轮次上限、凭证引用；凭证存 Windows 安全存储，不混入业务备份、日志或安装包。
- 最小执行能力：探测、运行、取消；按实际能力开放查询执行状态、继续会话、打开外部会话。缺失能力时不展示对应按钮。
- 统一结果：继续使用 summary、unknowns、sources、actions 的候选格式。受管讨论先核对再保存；外部 MCP 的直接业务命令仅在用户明确授权和相应连接权限内执行，不能通过换一个入口绕过权限。
- 可理解的状态：未配置、认证可用、业务接口可用、执行中、等待核对、已保存。桌面会话关联另列，避免再次把“配置好了”当作完整连接。
- 对话身份：本地 conversation_id 始终属于业务事项；外部绑定使用 provider_id + profile_id + external_thread_id + data_epoch。不同厂商的会话 ID 不统一假设为 UUID。
- 稳定执行：每个任务固化发送时的提供方、模型和配置。切换默认助手只影响新任务；跨助手继续时明确是带着选定上下文新开执行，不宣称恢复另一个厂商的原会话。
- 可靠恢复：未知发送结果先查询，不自动重发；业务写入坚持原 request_id。停止接收与远端真正取消分开，迟到结果不得重新落地。
- 通用 MCP 的受管绑定：目前 x-codex-turn-metadata 属于 Codex 专用身份依据。新客户端必须有独立可核验的绑定协议或专用受限连接，不能信任模型自己填写任意 conversation_id。

TokenHub 首期也不能只是加一个请求地址：软件要负责工具循环、白名单、候选截断处理、调用预算和终止条件。每次只传用户选定事项需要的上下文；不默认上传整个数据空间。

**六、原建议分批交付（当前进度见交接）**

| 批次 | 重点 | 可独立验收的交付物 |
| --- | --- | --- |
| A，建议立即做 | 纯手动基本闭环 | 主次入口调整、快速单项录入、未定日期任务池、整合单日安排、依赖编辑、无计划反馈、课程基础资料、结构化规则新建、教程同步 |
| B | 多任务效率与跨日能力 | 批量接口、拆分任务、日期范围草稿、计划先后校验、原子保存、限定撤销 |
| C，可与 A/B 并行做小范围验证 | 通用接口底座与三家接入验证 | Codex 薄适配；TokenHub 文本候选；CodeBuddy 与 WorkBuddy MCP 最小闭环。验证不绑定手动版本发布日期 |
| D | 验证通过的渠道产品化 | 优先软件内 TokenHub；CodeBuddy 正式执行器；WorkBuddy MCP 使用向导；统一状态、权限与恢复 |
| E，条件满足后 | 更深的 WorkBuddy 与桌面联动 | 完成授权方案和可信会话路由验证后，再支持软件主动派发、续聊与导航；不先承诺与 Codex 完全对等 |

独立周期任务与更丰富的资料转录可作为后续手动增强，不塞进 A。日期和工期应在 A 的交互验收及 C 的接口验证后确定，避免把所有功能绑成一次大改版。

**七、验收门槛**

首批 A 的验收至少包括：

1. 无 Codex／CodeBuddy／WorkBuddy、没有密钥且网络关闭时，完成建课程→连续录入任务→设置依赖→安排今天→调整→执行→复盘→回读。
2. 连续录入 10 个事项无需反复开关表单；标题之外的信息可后补。
3. 没有日期和归属的任务可从集中任务池找到，跨页筛选与选择结果一致。
4. 未先排计划也可记录真实完成或出勤，仍显示无原计划，不自动增加掌握／提交事实。
5. 课程评分、笔记、日程和全部分页可以手工维护；新增容量和保护时段无需发送对话。
6. 修改已有计划保留原身份与完成历史；完成标准的界面提示与后台规则一致。
7. 切换日期、关闭窗口和重启可恢复未保存草稿或得到明确处理提示；失败信息保留输入。
8. 关闭助手后，手动页面没有断连警告，也不创建模型任务；辅助功能失败不影响手动保存。

B 增加：跨日先后可计划但不假定已完成；固定日程与容量冲突可定位；并发修改与部分失败可解释；不出现半周悄悄保存；撤销不抹除真实历史。

每个新助手分别验收：读取当前事实→给出候选→在软件确认→助手回读；错误凭证、限流、断网、权限拒绝、取消后迟到、重启恢复、重复发送和同名外部 ID 都有明确结果。若宣称桌面联动，还需额外验收创建、项目归属、原会话继续、历史打开与双向消息；MCP 成功不能替代这一组验收。

测试继续补入现有 tests/ 和 packaging/check.py，按改动范围运行，保留最近报告并回收测试数据；不为每个提供方、每轮测试产生一套一次性脚本。
