# Codex 接口与任务处理

适用于个人事务管理 v1.0.0。软件界面、普通 MCP 对话和受管讨论共用同一个本机业务服务。本文说明接口语义，不包含个人会话、安装日志或本机验收记录。

## 连接与进程职责

| 组件 | 职责 |
| --- | --- |
| 桌面 GUI | 展示记录、提交明确操作、核对候选；不直接写数据库 |
| 本机业务服务 | 事务、版本校验、回执、定时工作和 Codex 连接 |
| MCP stdio 进程 | 把调用转给同一数据空间的业务服务 |
| 正常 Codex 桌面 | 在当前用户的 Codex 会话中执行模型回合 |
| 可选独立后台模式 | 单独运行 App Server；不保证实时显示在当前桌面 |

“设置 → Codex 协助”的“保存设置”和“连接 Codex”职责不同：保存偏好与受管理文件，连接时核对固定项目并建立实际桌面通道。启用桌面共享后，业务服务自动发现已经运行的普通 Codex。两端可按任意顺序启动；任一端重开后重新发现连接和原事项。

状态查询不会反复启动已关闭的 Codex。明确连接或发送可使用 Windows 注册入口激活当前 Codex；不要求替换快捷方式、设置全局环境变量或运行特殊连接模式。主窗口、设置和讨论显示同一实际状态。配置存在、桌面已连接、某一轮实际完成 MCP 调用是不同证据。

Windows MCP 启动业务服务时使用系统现有的本机进程启动能力，不安装 Windows 服务或计划任务。关闭 GUI 或 MCP 客户端，不等于停止独立业务服务。软件不负责 Windows 登录自启动，电脑关机或睡眠期间不运行任务。

## MCP 配置

普通用户优先通过软件设置完成配置。数据空间下的 `Codex事务助手` 是固定项目，项目级配置声明 `personal_management`。

开发接入示例，须替换为自己的绝对路径：

```toml
[mcp_servers.personal_management]
command = 'C:\Applications\PersonalManagement\PersonalManagementService.exe'
args = ['--mcp', '--data-dir', 'C:\Data\PersonalManagement']
```

源码环境可将 command 指向虚拟环境 Python，args 使用 `-m management.mcp_server --data-dir ...`。GUI 与 MCP 必须指向同一数据目录。

配置管理只维护本项目的受管理文件和必要信任项。已有明确拒绝信任或自定义内容冲突时保留原内容并报错，不覆盖其他项目、全局模型或账号配置。受管理文档及区块带内容哈希，升级先校验再原子写入。

项目级 `model_instructions_file` 引用受管理指令文件，要求每轮先读取实际绑定状态。保存文件不等于所有已经加载的 Codex 会话都已热更新；出现兼容性提示时需核对原会话状态，不能自动换建同名会话规避。

## 普通对话与受管事项

身份由 Codex 的真实调用元数据与业务服务保存的关联共同决定，不由聊天标题、模型自行填的参数或最近一次 GUI 选择决定。

| 类型 | 允许的业务路径 |
| --- | --- |
| 普通、从未绑定软件事项的项目对话 | 读取最新上下文后，直接执行用户已授权的确定性业务命令 |
| 已绑定当前软件事项的对话 | `begin_discussion` → 分页读取 → `validate_candidate` → `submit_candidate`；用户在软件中确认采用 |
| 历史绑定、失效绑定或数据身份冲突 | 明确报错，不降级成普通可写对话 |

新轮次先调用 `begin_context`。受管事项禁止通过直接写工具、采用候选或另建 AI 作业绕过当前工作流；普通对话不需要为了完成自身推理再调用 `send_message` 或启动另一模型。

标准工具包括：

| 用途 | 入口 |
| --- | --- |
| 状态、能力、字段和对象 | `begin_context`、`query_business`、`list_entities`、`get_entity` |
| 按需读取与长资料 | `prepare_context`、`query_context`、`read_context_item`、`next_context_step` |
| 检查点与证据刷新 | `checkpoint_context`、`operation_status`、`refresh_context` |
| 创建、修改与事实反馈 | `create_entity`、`update_entity`、`record_feedback` |
| 单日计划 | `planning_context`、`save_plan`；完整命令用 `execute_command(create_plan/revise_plan)` |
| 复盘、资料、课表、规则等 | `query_business` 和 `execute_command`，按当前 capabilities 的白名单 |
| 受管候选 | `begin_discussion`、`validate_candidate`、`submit_candidate` |
| 不确定写入核对 | `recover_receipt` |

核心计划字段 `minutes` 要求整数；使用通用命令时遵循核心 schema，不以工具包装层的宽泛数值类型替代业务校验。已有计划应先读取原版本，再使用修改计划入口保留历史，不盲目重复创建同日计划。

## 事务与回执

每条直接业务命令携带当前 `epoch`、`expected_revision` 和稳定 `request_id`；对象编辑还需准确的实体 `version`。

- 同一请求编号、同一内容可恢复同一回执；同编号不同内容会被拒绝。
- 版本冲突先重新读取并评估，不是只替换版本号重试。
- 超时先查询原回执；不把新请求编号当成安全重试。
- 备份恢复或切换数据空间后，旧数据身份不能继续写入。
- 模型回复、候选接收回执和正式采用回执具有不同含义。

候选采用在同一业务事务中重新核对相关证据、范围、硬约束和每条动作。任一动作不合法则整批不保存。长候选可分批暂存、分页核对，最后采用整份封存清单，不只采用预览页。

直接执行多条 MCP 命令则是多次独立事务。前几条成功、后续失败时，不会自动回滚前面的成功写入。

## 日期范围与事项连续性

软件每日计划入口绑定一个明确日期，计划专用请求只允许该日的一份计划候选。课程、对象和复盘同样保留原范围；在原对话中提到另一日期或对象，不会自动迁移归属。

普通未绑定项目对话可以接受一段时间的请求，逐日读取固定安排、现有计划、规则和任务，再逐日保存。当前没有专门的区间排程 API 或多日 GUI。一般候选机制能在一个事务中采用多个合法动作，但不能因此宣称已具备完整、自动的多日排程产品能力。

默认上下文按一个日期组织。计划、反馈和生效规则锚定该日，日程与临近截止使用有界窗口；范围外信息要继续读取，不能以一个日期的索引代表整个期间。跨日安排中的“前一天计划做完”不是实际完成证据；依赖校验不会自动把它当成前置已经完成。

已有计划的明确反馈与过去条目受保护，修改应使用 `revise_plan` 或计划专用候选流程。新任务估时不改变完成条件，未知时间、出勤、提交和掌握不能推断成已确认事实。

发送新消息会使该事项尚未采用的旧候选失效，以便新轮次按当前事实处理；已保存业务记录不会因此撤销。其他对话共享保存后的业务事实，不自动合并聊天全文。

## 正常桌面共享路径

桌面共享由业务服务持有连接，包含版本相关的 Codex 桌面私有 IPC 适配。官方 App Server 和私有桌面路由是不同接口层；不能把私有适配称为 OpenAI 的稳定公开桌面自动化 API。

发送时会：

1. 持久保存作业与唯一派发意图，核对项目、桌面身份和事项关联。
2. 对新事项用官方 App Server 创建持久空会话，确认保存后通过正常桌面入口打开；创建阶段不运行模型。已有事项沿用原会话。
3. 发现真实桌面所有者，订阅有版本的快照和增量，核验空闲与原回合状态后派发一次。
4. 通过固定项目 MCP 读取证据并提交候选。
5. 同时核对候选持久状态及对应模型回合的真实终态，再结算原作业。

派发记录按数据身份、作业和阶段去重。连接恢复只恢复观察和核对，不凭空再发模型。送达未知时优先关联原客户端消息标识、精确回合及只读历史；空闲、暂时查不到回合或未带完成时间的状态不能单独作为安全重发依据。

客户端、进程路径和 Windows 包身份不符合预期，或私有协议不兼容时，明确停止并说明。不会静默切到旧 Codex 或独立后台模式。

共享模式在正常 Codex 环境中运行。软件明确设置本轮只读文件权限等约束，业务 MCP 再单独守住受管范围；这不等同于隔离了用户 Codex 中所有其他工具或外部连接器。普通对话的外部操作仍需相应用户授权。

## 中断、取消与恢复

GUI 关闭、连接断开和业务服务停止不是用户取消。服务重新启动时核对原作业与回合，恢复订阅，不以重新发送替代恢复。

显式取消只可针对已核实的当前回合；身份未知时只能保留未知结果，不能宣称远端已停止。取消后迟到候选不自动采用。

“从已保存进度继续”只适用于具备有效检查点、原会话身份可核对、当前数据身份一致且没有冲突活动任务的失败或取消作业。恢复沿用原业务作业并进入新处理代次；旧回调不能覆盖新代次进度。同代次服务重开保留正确的已有进度。

压缩请求被接收不等于压缩完成。只有对应的已完成回合与上下文压缩证据核实后，才推进阶段预算。超时、丢页或身份冲突保留检查点，不自动重复压缩或创建替代事项。

## 分批上下文与资料

当前上下文协议提供小索引、分页详情、材料自然单元与持久检查点。初始索引、单页、单阶段、工具调用和图片都有预算，预算限制用于控制每次处理量，不是把整份长文档固定截成前几页。

长 PDF、课表和其他支持资料可以按批继续读取；整份“最多8页”的旧限制不再适用。来源不足、无法解析、未读完或多份资料矛盾会保留为缺口。普通进度反馈可只读取相关资料，不强制重做整门课程的分析。

每批候选最多30个动作，分批累计清单可以超过这个数；单日计划仍最多100个块。资料读取完整性、模型分析完整性和业务采用是三个独立状态。

## 可选独立后台模式

“仅在管理软件中处理”使用独立 stdio App Server，采用该子进程的工具隔离配置，不改全局 Codex 配置。非预期工具、审批或外部请求会停止本次处理。该模式不保证实时出现在用户当前桌面，也不是共享模式失败时的自动回退。

两种模式均使用同一业务事实、上下文校验和候选生命周期。v1.0.0 已完成日常使用体验验收；接口实现、自动化检查与个别端到端场景不代表全部设备、所有 Codex 版本及长期运行矩阵均已验证。
