## 4. 已完成：B1 批量录入与任务拆分

- “任务”页可批量录入，也可从任务页或任务详情拆分大任务。支持每行标题或五列 TSV：标题、完成标准、预计分钟、截止日期、安排日期；未知估时与日期可留空。
- 批量创建 1–50 项；拆分 2–50 项，每项子任务必须有独立完成标准。最多 500 条关联，规范化输入最多 180 KiB；超限明确分批，不假装无限原子操作。
- 先调用只读 `preview_task_batch`，再把返回的命令、完整 payload、`preview_token`、epoch、revision 与稳定 request_id 用于 `create_task_batch` 或 `split_task`。改动输入、版本或相关数据后重新预览。
- 在一次 Core 事务内创建全部任务、关联、批次审计与回执；中途失败整体回滚。不能在客户端循环发独立 `create` 后把部分成功称作整批成功。
- 子任务使用原生 `parent_id`，同时有指向原任务的 `contributes` 来源关联。每一个子任务都继承原任务的直接前置要求；明确勾选“依次完成”才添加相邻任务链。
- 原任务 ID、状态、完整完成标准、计划和反馈保留；已有后续仍依赖原任务。所有子任务完成不会自动完成原任务，补课范围和累计进度也不会分摊给子任务。再次拆分是追加，不替换已有子任务。
- 保存结果未知时锁定原提交；重试仍用同一请求。随后再遇到后台不可用、升级、认证、协议或数据空间错误，也不能丢掉第一次未知请求而创建新批次。
- 保存成功展示真实新任务，原任务详情可分页打开子任务。表格支持上/下移；大字号下编辑区可滚动，预览与保存按钮保留可操作位置。

主要实现：[task_batches.py](../src/management/task_batches.py)、[gui_task_batch.py](../src/management/gui_task_batch.py)、[core.py](../src/management/core.py)。

明确限制：本期没有批量修改旧任务或整批一键撤销；批次审计会阻止不安全的通用 undo。填写安排日期不自动创建每日计划。批量录入窗口未提交的表格没有跨重启草稿；它与 A 的单日计划草稿是不同功能。

## 5. 两类助手入口与业务接口边界

在同一环境内部，GUI、普通 MCP、受管候选和后台作业最终使用该环境的同一本地业务服务、Core 规则与数据库，不能为解决某个入口的问题建立额外的入口专属数据库或直接修改 SQLite。正式版与 Beta 分属两个独立环境，必须分别运行自己的后端、数据库和配置。

| 入口 | 写入规则 | 本轮 B1 支持 |
| --- | --- | --- |
| 普通、未关联软件事项的 MCP 对话 | 按用户授权调用业务命令，版本、事务和回执仍需校验 | 可预览并执行两种批量命令 |
| 软件发起并绑定事项的受管讨论 | 先提交候选，用户在软件核对采纳后修改实际记录 | 本轮没有扩展候选白名单，不能直接使用两种批量写命令 |

`received: true, applied: false` 表示候选已收到但尚未采用，不能称业务记录已修改。真正落地看业务回执，必要时回读实体和当前计划；模型文字、聊天完成或连接图标都不是写入证明。

普通 MCP 的 `preview_task_batch`、`task_pool`、`actual_feedback` 已支持长结果保真分页。续读需保留原查询、位置和版本，拼齐原始结果后再用原 payload/token 提交。预览输入本身过大、无法容纳续读信封时，明确返回 `business_page_budget`，不截断后继续写入。

参考：[mcp_server.py](../src/management/mcp_server.py)、[mcp_pages.py](../src/management/mcp_pages.py)、[mcp_routing.py](../src/management/mcp_routing.py)、[ai_commands.py](../src/management/ai_commands.py)、[Codex 接口](Codex接口与后台推理.md)。

## 6. 重要历史问题与保留的处理原则

1. **保存设置不等于实际连通。** 曾发生必须反复保存、重启或拉起错误客户端的问题。连接方案应接入正常启动的客户端，分别核对项目准备、桌面通信、任务执行、结果回传和会话可见性；单项通过不能代替全部验收。
2. **源码更新不等于所有入口更新。** GUI、独立后台和 MCP 都可能仍运行旧程序。迁移或升级后按实际程序/数据身份与能力回读，不能靠接口名称或界面版本猜测。
3. **“修改计划未注册”不是只能在 GUI 修改。** v1.0.1 修复过因能力目录响应裁剪导致的注册误判；完整能力检查与对外有界展示应分开。计划修改引用当前计划 ID 与版本建立正常修订链，通过 `supersedes_id` 连接前版；不能用普通新建产生重复的并行当前计划，也不原地重写受保护历史。见 [v1.0.1](发布说明_1.0.1.md)。
4. **计划先后与实际完成分开。** 前置任务出现在计划里，不证明它实际完成；没有反馈不能推断缺课、失败、已提交、掌握或实际用时。当前日期相关完成投影比实体原始 status 更准确。
5. **前置必须给所有拆分子任务。** 若只给第一项，第一项后来被单独确认完成时，后续可能绕过原前置。来源关联 `contributes` 也不代替 `depends_on`。
6. **结果未知必须持续保留请求身份。** HTTP/协议/服务异常可能发生在事务提交之后；重连失败也不能证明原请求未写入。只有可靠回执或明确业务拒绝才允许结束该次提交。B1 当前保证窗口内原请求保留，不承诺批量窗口在进程崩溃后自动恢复。
7. **保护完成历史与删除语义。** 不因拆分、编辑备注或降低标准重写旧反馈。已删除任务详情保留恢复流程，本轮曾因新增子任务查询破坏旧约定，已修复并保留验收。
8. **不从文本推断任务结构。** 一个大任务说明中的编号不是独立任务，文字顺序不是依赖。只有明确输入、关系和保存回执能形成系统状态。
9. **后台关闭与退出是两件事。** 关闭主窗口可以留在托盘；退出和更新应走正常入口，保护未保存编辑与正在执行的作业，不强杀或误清正在使用的目录。见 [v1.1.0](发布说明_1.1.0.md)、[v1.1.1](发布说明_1.1.1.md)。
10. **研发范围要跟随用户这次指令。** 曾有仅交接/检查却提前实现任务池的越界改动，已按用户要求回退；后续 A/B1 是得到明确授权才重新实施。读取旧方案不等于现在获准实施全部方案。

### 2026-10-06 用户数据空间与迁机核对（源码只读，尚未整改）

用户要求软件面向每位用户创建或选择自己的数据库，不能依赖开发者机器的盘符、用户名或资料目录。运行时解析出的绝对路径用于本机访问与连接身份校验，不能等同于把开发者路径固化到产品，也不能简单全部替换为相对路径后取消隔离校验。

- 正式工作树源码的新用户默认路径来自当前用户的 `LOCALAPPDATA/PersonalManagement/data`，安装器支持自选目录并登记在当前用户配置中，没有写死开发者盘符或用户名。以上是源码与测试定义核对，未检验当前运行的 1.2.1 二进制，也未启动或修改正式环境。
- 发现普通启动的缺口：此前选择的数据目录搬走后，只要原路径仍可创建，存储初始化可能自动建空库。安装/升级已有“旧库缺失时拒绝换空库”的检查，普通启动尚未区分明确新建与打开旧库。后续需优先增加打开旧库的存在性与身份核对，找不到时提示重新定位，不能静默替代。
- 当前选择空间只影响本次启动，持久入口另依赖快捷方式/安装登记。应统一用户创建、打开、切换及记住空间的流程，并在迁机后重建本机入口；不把数据库本体随程序或源码发布。
- 受管资料的 `blobs` 和原文件索引使用空间内相对路径，原始绝对路径通常只是来源记录；外部文件引用则仍依赖原路径，需要重新关联或先转为受管副本。
- 整目录复制会携带旧 `runtime.json`，因旧数据路径身份不符而拒绝连接；它含本机服务身份，不应盲目改写后复用。既有备份/恢复只带数据库及受管内容，重建 epoch、取消未完成作业并清理运行绑定，是当前受支持的迁移方向。
- Beta 目前仍是源码开发通道，只接受当前工作树 `.beta-data`；默认按工作树区分，不按 Windows 登录用户自动各建一份库，多人共用同一工作树会选中同一 default。这不是面向其他用户的最终安装版数据选择方案。演示 journal 还绑定首次数据目录，未完成步骤也可能引用旧路径，搬迁后不能只改一个目录字符串就续跑；恢复后的演示可浏览，重新生成应使用新空间。
